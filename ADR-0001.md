# ADR-0001: SmartEnum base (`EnumModel`) provided by the owned `IndQuestEnums` package

- **Status:** Proposed (package to be built/published out-of-band; EMIP references it once available)
- **Date:** 2026-06-09
- **Deciders:** hebelmx (architecture owner)
- **Context stories:** Story 1.2 (Domain ontology & shared value types) — first consumer
- **Related:** ADR rule 14 (Domain records carry no persistence attributes); `ARCHITECTURE_AND_SOLUTION_GUIDELINES.md` §5.5 (SmartEnums); the owned `IndQuestResults` package (precedent for an owned foundational Domain dependency)

## Context

The house style mandates SmartEnums that derive from an `EnumModel` base (sealed class, static readonly instances, `FromValue`/`FromName` factories, EF value-converter + comparer). EMIP needs this base for `Confidence`, `FaultClass`, `ControlStrategy`, and `ZoneTag` (Story 1.2 AC-5).

No such base exists in EMIP yet, and `IndQuestResults` (the owned `Result<T>` package) does **not** ship one. Two divergent in-house copies already exist across the estate:

| Source | Notes |
|---|---|
| `IndTrace` `…/Core/Domain/Enum/Enumeration.cs` | The original. Linear `FromValue`. **Carries a `displayName` assignment bug** (assigns the unset `DisplayName` property instead of the constructor parameter, so display names silently collapse to `Name`). Couples to `LookUpTable`/`ILookUpTable`. |
| `ExxerCube.Prisma` `…/01 Core/Domain/Enum/EnumModel.cs` | "Production-tested, ported from IndTrace." Bug **fixed**; adds an O(1) thread-safe `ConcurrentDictionary` lookup cache. Couples to `IEnumModel`/`ILookupEntity`/`EnumLookUpTable` + an `EnumModelConversions.cs` EF helper in Infrastructure. |

Copying a **third** variant into EMIP guarantees continued drift, and a copy carrying the IndTrace display-name bug would regress a fix Prisma already made.

A separate question: should the base be bundled into `IndQuestResults`, or be its own package, or stay in-house "for domain purity"?

## Decision

1. **Create a dedicated owned NuGet package `IndQuestEnums`** (named for consistency with `IndQuestResults`) as the single source of truth for the SmartEnum base across IndTrace / Prisma / EMIP / future solutions. Build it **outside the EMIP repo/context** (own repo under `E:\Dynamic\IndFusion\IndQuestEnums`) so this cross-cutting concern does not contaminate feature work.
2. **Do NOT bundle it into `IndQuestResults`.** A railway-error-handling library and a DDD SmartEnum base are distinct concerns; bundling forces every `Result<T>` consumer to take the SmartEnum base, couples their semver, and erodes package cohesion. `IndQuestEnums` follows the *pattern* of `IndQuestResults` (owned, foundational, Domain-safe) without riding *inside* it.
3. **Keep the package core dependency-free** (no EF, no lookup-table machinery) so it is safe to reference from a pure Domain. Provide the EF value-converter + comparer in a **separate companion** (`IndQuestEnums.EntityFramework`) consumed only by Infrastructure. The `ToLookUpTable`/`ILookUpTable` projection from the legacy copies is **dropped from the core** (re-add to a companion if a consumer needs it).
4. **Base the implementation on the Prisma (bug-fixed + O(1)-cached) version**, not the IndTrace original — carrying the display-name fix forward.
5. **EMIP depends on `IndQuestEnums` via `PackageReference`** (centrally pinned in `Directory.Packages.props`). This is consistent with how `IndQuestResults` is already a referenced owned package — "domain purity, kept in-house" is satisfied because the package is *our* code, just versioned and de-duplicated, not a third-party dependency.

## Consequences

**Positive**
- One bug-fixed source of truth; the IndTrace/Prisma divergence stops propagating.
- Domain stays pure: the core has zero external dependencies; EF coupling is quarantined to a companion used only in Infrastructure.
- Cross-cutting work is isolated from EMIP feature context (built/published in its own session).

**Negative / costs**
- A new package + publish pipeline is out-of-band work that must complete before EMIP Story 1.2's SmartEnum task (AC-5) can finish. The other Story 1.2 tasks (ontology, value objects, `EngagementCase`) are unblocked.
- EMIP carries a hard dependency on a freshly-published package; its version must be pinned and the feed reachable (note: `nuget.config` is nuget.org-only + `clear`, so `IndQuestEnums` must publish to nuget.org or a private feed must be added).

**Follow-ups**
- When `IndQuestEnums` is published: add `<PackageVersion Include="IndQuestEnums" Version="x.y.z" />` to `Src/Directory.Packages.props` (next to `IndQuestResults`), reference it from the Domain csproj, and add `global using IndQuestEnums;` to Domain `GlobalUsings.cs`.
- Migrate IndTrace and Prisma to the package opportunistically (retire their local copies).
- Supersede this ADR's status to **Accepted** once the package is published and referenced.

## Alternatives considered

- **Bundle into `IndQuestResults`** — rejected (cohesion/semver coupling; forces unrelated dependency on every Results consumer).
- **Port a trimmed copy in-house into EMIP `Domain/Common/`** — viable as a tactical unblock, but rejected as the destination state because it would become a third divergent copy. (If velocity demands, a *provisional* in-house port behind this ADR is acceptable, to be swapped for the package reference on publish.)
- **Keep using the linear IndTrace original** — rejected (carries the display-name bug; no O(1) lookup).
