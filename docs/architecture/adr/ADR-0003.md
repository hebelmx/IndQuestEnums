# ADR-0003: Opt-Out of C# 15 / .NET 11 `union` Types and `closed` Hierarchies for `EnumModel` SmartEnums

- **Status:** Accepted (Opted Out — Deferred for Future Re-evaluation if CLR/Language Lowering Changes)
- **Date:** 2026-11-15
- **Deciders:** hebelmx (architecture owner), evaluated via BMAD v6.12.4 Party Mode Architecture Review (Winston / Amelia / Mary / John / Sally)
- **Target Frameworks Evaluated:** `net10.0` (LTS) and `net11.0` (STS) with C# 15 (`SDK 11.0.100`)
- **Related:** [ADR-0001](ADR-0001.md) (SmartEnum base `EnumModel` provided by `IndQuestEnums`), [ADR-0002](ADR-0002.md) (Drop-in `InvalidValue<T>()` resolver, `InvalidState` constant, and in-core JSON converter), sibling `IndQuestResults` ADR-001

---

## Context

With the release of **.NET 11** and **C# 15**, two algebraic data type (ADT) features were introduced to C#:
1. **Union Types (`public union U(A, B)`)** and the custom `[Union]` / `IUnion` pattern.
2. **Closed Hierarchies (`public closed abstract class` / `public closed record`)**, restricting direct inheritance to the declaring assembly and enabling compiler-verified exhaustive `switch` expressions without a discard (`_ =>`) arm.

Because strongly-typed enumerations ("SmartEnums") are often compared to discriminated unions in functional programming literature, we conducted due diligence and a full BMAD Party Mode architectural review to evaluate whether `IndQuestEnums` (`EnumModel` and `IndQuestEnums.EntityFramework`) should adopt C# 15 `union` types or `closed` hierarchies alongside our `.NET 11` (`net10.0;net11.0`) multi-targeting upgrade.

---

## Decision

**We are opting out of introducing C# 15 `union` types and `closed` hierarchies into `IndQuestEnums` at this time.**

- `EnumModel` remains a `public abstract class` designed for cross-assembly inheritance by downstream Domain projects (`IndTrace`, `ExxerCube.Prisma`, `EMIP`/`CubeXplorer`).
- Derived SmartEnums remain `public sealed class` types declaring `public static readonly` singleton field instances with a non-throwing `Invalid` sentinel.
- Both `IndQuestEnums` and `IndQuestEnums.EntityFramework` now multi-target **`net10.0;net11.0`** while preserving 100% binary, source, and wire-format compatibility.

---

## Technical Rationale

### 1. `closed` Hierarchies Prohibit Cross-Assembly Inheritance
In C# 15, marking a base class `public closed abstract class` restricts direct inheritance **exclusively to the declaring assembly** (`IndQuestEnums.dll`).
- The foundational purpose of `IndQuestEnums` ([ADR-0001](ADR-0001.md)) is to serve as a reusable NuGet base class inherited by domain types in consumer assemblies (`public sealed class ZoneTag : EnumModel`).
- Applying `closed` to `EnumModel` would cause an immediate compiler error in every downstream consumer assembly.

### 2. Value-Identity Singletons vs. Type-Identity Subclasses
`EnumModel` models an enumeration as a **finite table of singleton instances sharing a single CLR `Type`** (`ZoneTag.Z1`, `ZoneTag.Z2`, `ZoneTag.Invalid` are all instances of `ZoneTag`), indexed by a stable PLC/persistence `int Value`. By contrast, C# 15 `closed` hierarchies and `union` types enforce exhaustiveness **by distinct CLR runtime type** (`case Z1Type:`, `case Z2Type:`).

Refactoring derived SmartEnums so that each member is a nested `sealed class` inside a `closed abstract class ZoneTag : EnumModel` would break every core mechanism of the library:
- **Reflection & Discovery Breakage:** `EnumModel.GetAll<TEnum>()` scans `BindingFlags.Public | BindingFlags.Static | BindingFlags.DeclaredOnly` fields on `typeof(TEnum)`. Nested subclasses are not fields.
- **`where TEnum : new()` Factory & Converter Breakage:** `EnumModel.FromValue<TEnum>(int)`, `EnumModelJsonConverter<TEnum>`, and `EnumModelConverter<TEnum>` (EF Core) require `where TEnum : EnumModel, new()`, and `EnumModelJsonConverter.CanConvert` explicitly rejects `typeToConvert.IsAbstract`. An abstract `closed` parent enum type cannot satisfy `new()` or rehydrate without polymorphic reflection.
- **Type-Equality Invariant Breakage:** `EnumModel.Equals(EnumModel? other)` compares `this.GetType() == other.GetType() && this.Value == other.Value`. Distinct runtime subclasses per enum value would require changing equality semantics and defeat reference-equality assumptions.
- **Declaration Bloat:** Replacing one-line `public static readonly ZoneTag Z1 = new(1, "Z1", "...");` declarations with 4–6 lines of nested subclass boilerplate per enum member degrades domain readability across 20+ member industrial/PLC enumerations.

### 3. Immaturity of C# 15 `union` Lowering (`IUnion.Value` Boxing & Ceremony)
- Standard C# 15 `public union` lowers to a struct implementing `System.Runtime.CompilerServices.IUnion` with an `object? Value` property, boxing value-type payloads onto the heap.
- A C# 15 `union` cannot serve as a base class, provides no `(int Value, string Name, string DisplayName)` triple, no O(1) `ConcurrentDictionary` `FromValue(int)` cache, no graceful `Invalid` sentinel fallback (`InvalidState = -1`), and no compatibility with `EnumModelJsonConverter` (~1,600×/report hot path) or EF Core `ValueConverter<TEnum, int>`.

### 4. Prior Source Generator Evaluation & Agentic Era Context
The only developer-ergonomics gap between `EnumModel` and a language-level sum type is compile-time `switch` exhaustiveness over `static readonly` instances.
- Currently, `EnumModel` provides `public static implicit operator int(EnumModel model) => model.Value`, allowing high-performance `switch ((int)enumInstance)` over `const int` keys when jump-table switching is needed.
- We previously evaluated Roslyn Source Generators (prior to the agentic programming era) to auto-generate `const int` tags or exhaustive `Match` helpers. While technically a clean fit, the maintenance overhead did not justify the ROI at the time. In the current agentic era, keeping `EnumModel` small, predictable, reflection-warmed, and dependency-free remains the highest-leverage design.

---

## Consequences

**Positive**
- Zero breaking changes for `IndTrace`, `ExxerCube.Prisma`, and `EMIP`/`CubeXplorer` (preserves the drop-in contract established in [ADR-0002](ADR-0002.md)).
- Full support for `.NET 11` (`net10.0;net11.0`) out of the box with zero `IUnion` boxing or polymorphic converter overhead.
- Architectural due diligence is recorded so downstream teams do not waste cycles attempting to force `EnumModel` hierarchies into C# 15 `union` or `closed` constructs.

**Negative / Trade-offs**
- `EnumModel` instances (`public static readonly`) still cannot be used directly as C# constant `switch` arms without matching on `.Value` / `(int)` or `if/else` chains.

---

## Conditions for Future Re-evaluation

We will revisit this decision in a future C# / .NET release (e.g., C# 16+ / .NET 12+) **if and only if**:
1. **Value-Based Exhaustive Pattern Matching / Active Patterns:** C# introduces active patterns, `const`-like pattern matching over `static readonly` singletons, or extension-based exhaustive matching that works additively on a single `sealed class` without requiring a distinct subclass per enum member.
2. **Optional Source Generator / Analyzer Companion:** If downstream demand across `EMIP`, `Prisma`, and `IndTrace` ever justifies an opt-in `IndQuestEnums.Generators` or `IndQuestEnums.Analyzers` companion package to emit `Match(...)` methods or exhaustiveness diagnostics without altering the core `EnumModel` contract.
