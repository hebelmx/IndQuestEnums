# ADR-0002: Drop-in `InvalidValue<T>()` resolver, `InvalidState` constant, and an in-core JSON converter

- **Status:** Proposed (draft — package not yet governed; **Accepted on the 1.1.0 publish, which governance gates**).
- **Date:** 2026-06-28
- **Deciders:** hebelmx (architecture owner), pressure-tested in a party-mode round-table (Architect / Senior Eng / PM / Analyst / Tech Writer / UX).
- **Context stories:** IndTrace issue #37 (delete the in-tree `EnumModel` copy, consume `IndQuestEnums`) — first migration; surfaced every gap below.
- **Related:** [ADR-0001](ADR-0001.md) (the package exists; core was "dependency-free *and* concern-pure" — this ADR amends the concern-purity clause); the `InvalidValue` / `InvalidName` consts and the private `Invalid<TEnum>()` helper on `EnumModel`; IndTrace's local stop-gaps `EnumModelInvalid.Of(...)` and `EnumLookUp`.

## Context

`EnumModel` resolves an unmatched lookup to the *type's own* invalid sentinel — the `public static readonly Invalid` field on the derived type — via a **private** `Invalid<TEnum>()` helper. The legacy in-tree copies (IndTrace / Prisma) instead exposed this as a **public method `InvalidValue<T>()`**. The package made it private and added a `public const int InvalidValue = -1`.

The IndTrace #37 migration exposed three problems:

1. **No public way to get a type's `Invalid` instance.** A production cache converter reached for it via `typeof(EnumModel).GetMethod("InvalidValue")` — which post-migration returns `null` (the name is now a *const*, not a method). The failure was invisible to the compiler and silently degraded every enum whose `Invalid != -1` (`FlowStatus.Invalid = 8`) or whose `-1` slot is a real member (`ActiveStatus.Inactive = -1`, `Invalid = int.MinValue`) to a generic `-1` instance. `FromValue<T>(-1)` is the same trap.

2. **Migration friction.** The package goal is that a consumer upgrades by **adding a `using` and a `PackageReference` — zero call-site edits.** That is impossible while the legacy method name `InvalidValue<T>()` is unavailable.

3. **The "converter" is hot, and it dragged in EF.** Almost every enum-typed state is refreshed from persistence on each request *and* written back — the `int ⇄ EnumModel` conversion runs **~8×/request, ~1,600×/small daily report**. The *invalid fallback inside it* is rare ("maybe none is invalid"), but the conversion itself is firmly on the happy path. Consumers were hand-rolling this converter (the source of problem 1), and the natural home looked like the EF companion — pulling an **EF Core dependency** onto a path that does not actually need EF.

Naming constraints (empirically verified, net10.0 / current Roslyn):
- A base member literally named **`Invalid`** is hidden by every derived type's `Invalid` *field*: the **generic** `Invalid<T>()` compiles clean, but a **non-generic** `Invalid(Type)` triggers **CS0108** → a warnings-as-errors build break in every consumer. So `Invalid` is unusable for the `(Type)` overload.
- **`InvalidValue<T>()`** (the legacy method name) does **not** collide with the `Invalid` field (different identifier) — it is only blocked by **CS0102** against the existing `const int InvalidValue`. Free the const name and the legacy method returns.

## Decision

1. **Revive the legacy public API `InvalidValue<TEnum>()`, plus a non-generic `InvalidValue(Type)` overload** for converters/serializers that hold a runtime `Type` (intrinsic to value-converter frameworks — EF, STJ, cache). Both return the type's own declared `Invalid` singleton; **never null, never throw**; fall back to a fresh sentinel instance only when the type declares no `Invalid`. Reviving the *exact legacy name* is what delivers the **drop-in** goal: existing `InvalidValue<T>()` call sites compile unchanged.

   ```csharp
   public static TEnum     InvalidValue<TEnum>() where TEnum : EnumModel, new();
   public static EnumModel  InvalidValue(Type enumType);
   ```

2. **Resolve via reflect-once + eager warm — no reflection on any request path.** The package already warms a per-type lookup lazily on first `FromValue`; capture the `Invalid` member in that same one-time pass and cache it (O(1) thereafter). Add an **eager warm** hook (e.g. `Warm<T>()` / warm-all at converter registration) so the single reflection happens at startup, single-threaded, before any request — no first-request penalty, no lazy-init lock contention under concurrent load. (The accessor itself is a cold fallback; the warm matters for the *hot converter* in §4.)

3. **Rename `const InvalidValue` (int, `-1`) → `const InvalidState`.** Forced by CS0102 to free the method name, and a better name on its own terms: the value is not a "number" in the domain — it is the **invalid *state*, encoded as a number because PLC tags are not strongly typed**. The XML doc carries that rationale. **`const InvalidName` ("Invalid Value") is unchanged** — it was a deliberate prior semantic and renaming it would break drop-in for no benefit (no method competes for that name). The resulting asymmetry (`InvalidState` moved, `InvalidName` kept) is intentional and documented: the *value* const had to move to free the method name; the *name* const did not.

4. **Ship the hot STJ `JsonConverter<EnumModel>` in the CORE package.** `System.Text.Json` is **in-box** since .NET Core 3.0 (no NuGet reference), so this keeps the core's *dependency-free* promise (zero third-party packages) while **amending ADR-0001 §3's "concern-pure" clause**: a serialization *type* now lives in core. It is **opt-in** — shipping the type changes nothing until a consumer registers it. The converter is lean: serialize as the **`int`** value (not a `{Value,Name,DisplayName}` object), deserialize `int → FromValue<T>` off the warmed cache — **no per-call reflection, no per-call allocation.** Rationale: this is the ~1,600×/report hot path, and shipping the one correct converter stops every consumer re-rolling the reflection-by-string version that caused problem 1.

5. **Leave the EF companion (`EnumModelConverter<T>` / `EnumModelComparer<T>`) unchanged — version-bump only.** The EF `ValueConverter` genuinely needs EF Core and stays in `IndQuestEnums.EntityFramework` for consumers doing column mapping. It gets **no code change**, only a **lockstep bump to 1.1.0** so core and companion share a version and consumers pin one number without confusion.

6. **Semver: additive minor → 1.1.0** (core *and* companion). The only non-additive change is the `InvalidValue` → `InvalidState` const rename; its blast radius is near-zero (used only by the package's own tests and IndTrace's interim redirect, which this work removes).

7. **Governance gates the 1.1.0 publish.** Shipping a hot-path converter that three solutions depend on into a not-yet-governed package raises the stakes; the owner (hebelmx) is standing governance up alongside this release. Minimum bar is the owner's call; this ADR records that the publish does not happen before it exists.

## Backward compatibility

**Drop-in for the SmartEnum *value* API.** `InvalidValue<T>()`, `FromValue`, `FromName`, the operators — a migrating consumer needs only a `using IndQuestEnums;` (or global using) and the `PackageReference`/version bump. No call-site edits. **Honest scope:** this does **not** cover the lookup coupling the legacy copies grew locally — `IEnumModel`, `ToLookUpTable`, `ILookupEntity` were never in the package by design and still require a local shim (IndTrace's `EnumLookUp`; Prisma will keep its own). The const rename is the sole source break and is near-zero-usage.

## Consequences

**Positive**
- Consumers stop re-implementing the invalid resolver and the JSON converter; the correct, fast, cached version is the path of least resistance. The reflection-by-string failure class cannot recur.
- The hot conversion path loses per-call reflection and per-call object allocation; eager warm removes the first-request penalty and lazy-init contention.
- The EF dependency is confined to consumers who actually map EF columns; cache/JSON consumers take core only.
- Migration cost collapses to "a `using` and a version bump."

**Negative / costs**
- Amends ADR-0001's concern-purity stance (a serialization type now sits in core — in-box, opt-in, but a concern nonetheless).
- The in-core JSON converter changes the cache wire format (object → int). Tolerable for a **cache** (stale entries miss and repopulate); it must **not** be used where the old object format is persisted durably. Called out as a deliberate step, not a freebie.
- Two more public members and a renamed const to keep stable under semver.

**Follow-ups**
- Publish 1.1.0 (core + companion) once governance is in place.
- IndTrace: replace `EnumModelInvalid.Of<T>()` / `Of(Type)` with `EnumModel.InvalidValue<T>()` / `InvalidValue(Type)`, delete the local helper, and delete the hand-rolled `EnumModelJsonConverter` in favour of the in-core one (mind the cache wire-format change).
- Prisma: drop-in the value API; keep its local lookup shim.
- Add `IndQuestEnums.Tests` cases pinning both `InvalidValue` overloads for a non-`-1` `Invalid` (value 8) and a type whose `-1` is a real member, so the `FromValue(-1)` trap stays regression-covered.
- Supersede this ADR to **Accepted** on publish.

## Alternatives considered

- **`GetInvalid<T>()` / `GetInvalid(Type)`** — collision-free and was the working proposal, but rejected: `Get` reads as an imperative/cast, not the behaviour, and it is *not* the legacy name, so it forfeits the drop-in goal.
- **`Invalid<T>()` / `Invalid(Type)`** — shortest, but the non-generic `Invalid(Type)` triggers CS0108 against every derived `Invalid` field (verified) — a warnings-as-errors break.
- **`InvalidValue<T>()` while keeping the const** — impossible (CS0102). Renaming the const to `InvalidState` is the enabling move.
- **Static-abstract interface** (`static abstract TSelf Invalid`) for zero-reflection resolution — rejected: not additive (forces every derived enum to change field→property + implement the interface, re-touching wire-contract enums) for a cold fallback path; reflect-once+warm already removes reflection from the steady state.
- **Generic-only, no `(Type)` overload** — rejected: value-converter frameworks hand you a `Type`, so this just pushes `MakeGenericMethod` reflection back onto every consumer (the original bug).
- **Ship the JSON converter in a separate `IndQuestEnums.Json` companion** — rejected: `System.Text.Json` is in-box, so core can host it with no dependency cost; a third package would add friction against the "just add the dependency" goal.
- **Touch the EF converter in this release** — rejected: it works and nobody's blocked; lockstep version-bump only, smallest release that delivers the drop-in.
